## Equipment reentrancy review

The review found two additional ownership hazards in the initial implementation and corrected them before final freeze. A completion callback or `EQUIPMENT_APPLIED` listener can start **and synchronously finish** a newer request. Checking only `latestApply` would then see nil and let the older outer request overwrite the newer gear. A begin generation now preserves chronological ownership after synchronous completion.

The new request also owns its short supersession handoff before installation. Its exact callback can cancel during an older request's completion notification; cancellation settles it once and prevents later combat/lock/bank work. A callback started during supersession can replace the request, and each callback settles once. These cases execute the actual complete Equipment owner through callback and event entry. No-op cancellation emits no completion/inventory work, and cancellation of a foreign callback does not remove the newer request. Cancellation cannot undo item moves already accepted before cancellation.

## Preserved behavior and cost

The existing60ms picker/talent,480ms picker-hide,80ms bank withdrawal and0.3/0.5s mount deadlines remain. The learn loop still uses one operation per invocation with its existing optimistic state/resync policy. No feature, saved setting, command, modifier priority or TOC route was removed. Parent-owned Action/Paint usability, tint and darkening changes were consumed by verification but not edited by this slice. Existing alpha guards, bling threshold, swipe/edge, checked state and utility modifier lifecycle checks pass.

The collection index adds numeric spell→existing-entry references and two cache tables per collection/companion cache lifetime; it does not create entries per paint. Picker/learn work owns one request table per scheduled request; native timer cancellation bounds live pending work where NewTimer is available. Equipment deep-copies gear/rune snapshots once per request, using existing Compat.DeepCopy, and owns one request object. It introduces no idle driver. The reticle guard performs one existing option-policy check per active targeting tick and removes the disabled face scans. Operation counts do not establish native CPU, allocation cost or FPS.
